# 同步节奏评估：小步频繁合 vs 几个月一次

测量日期 2026-07-27。方法：在隔离 worktree 里，对 5 个时间切点各做一次真实 `git merge --no-commit --no-ff`（本地取该时刻的 main，上游取该时刻的 upstream/main，基座固定 ba38f908），统计冲突文件数与冲突块数（`<<<<<<<` 计数），随后 `merge --abort`。生产 checkout 全程未被污染。

## 漂移—冲突曲线

```
日期        上游领先   本地领先   冲突文件(源码)   冲突块
2026-06-01    204        45        10 ( 8)        24
2026-06-15    417        57        20 (13)        54
2026-06-29    701        58        23 (14)        71
2026-07-13    930        66        39 (18)       134
2026-07-28   1173        71        43 (20)       156
```

每 100 个上游 commit 产生的冲突块：11.8 / 12.9 / 10.1 / 14.4 / 13.3。**基本线性，约 13 块/百 commit。**

结论一：冲突总量对漂移时长近似线性，不是指数爆炸。所以「小合能把总冲突量砍掉一个数量级」是错的，砍不掉——每两周合一次，五次合完的冲突块总量大约 5×24≈120，对比一次性 156，只省约 25%。

**光看冲突数，小合的收益不大。真正的差别在另外三处。**

## 差别一：风险集中度

156 个冲突块全部压在运行时核心——loop.py 20、runner.py 15、anthropic_provider.py 9、memory.py 8、builtin.py 7、subagent.py 7。这正是 2026-05-18 那次事故的形状：没合完的冲突标记留在文件里，服务重启直接 SyntaxError 挂掉。

24 个冲突块是一个下午能读完、能逐块论证的量。156 个不是——它必然退化成「看起来能跑就提交」。

## 差别二：上游重构的可跟随性

按 2 周窗口统计上游对「我们改过的 39 个源码文件」的删除+重命名事件：

```
窗口          上游 commits   删除+重命名   涉及我们的文件
→ 06-01          204            8          无
→ 06-15          213            2          dream_phase1/2.md 被删
→ 06-29          284            0          无
→ 07-13          229            2          无
→ 07-28          243           21          discord.py → discord/runtime.py (R099)
```

结构性重构不是均匀发生的，它成簇出现。channels 插件化整个压在最后两周。

**在窗口内跟随，你能读到做这件事的那个 commit，照着它搬。70 天后再合，你面对的是五轮重构的复合结果，没有任何一个 commit 能解释当前形状。**

（补一个我先前说错的：我一开始判断「本地 202 行 Discord 改动落在一个上游已不存在的文件上」，这在机械层面是错的。R099 相似度让 git 自动跟随了重命名，`nanobot/channels/discord/runtime.py` 实际是 Auto-merging 通过的，只有 test 文件冲突。但自动合并成功不等于正确——我们的定制被塞进了一套 manifest/locales 插件架构里而没做适配，这个语义风险仍然存在。）

## 差别三：重复造轮子（最大的隐性成本）

这一项在冲突计数里完全看不见，却是本轮最贵的账：

- `c41b8717`（subagent 并发上限不生效）——上游 `cfabc29f` 修了同一个 bug，拒绝文案逐字相同。我们白写了一遍。
- `cb1dadfa` + `58cd1135`（手工 alias / provider swap 补丁）——上游把这件事做成了一等公民 `nanobot/utils/llm_runtime.py` 的 `ProviderSnapshot`。我们的补丁全部作废。
- `ced62a8c` ContextPruner——上游 `context_governance.compact_inflight_overflow` 是它的严格超集。而我们这份 `enabled` 默认 False，等于从没上线。
- `55b46a2f` Dream 单阶段重构——我们主动移植了 upstream `d1a94dae`，这次是对的，因为当时跟得近。

**跟得近的那一笔（dream）是净收益；跟得远的几笔全是废功。**

## 成本估算

一次 2 周期的同步：冲突块约 24，涉及源码文件约 8，加上跑测试和验证重启，**半天以内**。

一次 70 天期的同步：冲突块 156，源码文件 20，外加本轮额外要做的归属判定（71 个 commit 逐个比对上游）、结构适配（channels 插件化）、废功清理。**三到五天，且带生产事故风险。**

## 建议

**每两周一次，固定档期，不看上游有没有大动作。**

理由不是省时间——总时间省不了多少。理由是：把一个会引发生产事故的大爆炸，换成十次无聊的小操作；以及在上游做出等价实现的两周内就发现它，而不是 70 天后才知道自己白写了四笔。

配套三条：

1. **fork 表面积必须守住 39 个源码文件这个量级。** 它现在很小，这是小合可行的前提。每加一处对 loop.py / runner.py 的侵入式改动，就把未来每次同步的成本抬高一档。能做成 hook / plugin 的绝不做成 patch。
2. **每次同步在隔离 worktree 里做，生产 checkout 永不出现未完成的 merge。** 这是 2026-05-18 那次事故换来的规矩。
3. **同步前先扫一眼上游这两周的 CHANGELOG / 合并的 PR 标题**，看有没有跟我们 fork 功能重叠的——发现重叠就当场砍掉本地那份，别等它长大。
